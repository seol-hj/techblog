## GKE 운영 모드

1. **Autopilot** : 플랫폼 관리 위주 GKE
2. **Standard** : 운영자 제어 위주 GKE

### Standard 모드

- **더 많은 제어와 유연성** 제공
- 사용자가
	- 클러스터 인프라 제어
	- 대부분 설정 변경 가능
	- 노드풀 직접 구성
	- 노드 설정, 보안 정책, 스케일링 직접 설정

**특징**
- 사용자가 노드풀 직접 설계 가능
- 노드 구성과 머신 타입 선택의 유연성이 큼
- 보안 정책, 제약, 네트워크 설정을 더 세밀하게 조정 가능
- 운영 부담이 더 큼
- 필요 시 일부 워크로드만 Autopilot 방식으로 혼합 운영 가능

### Autopilot 모드

- Google이 **노드 인프라, 스케일링, 보안 기본 구성, 사전 설정된 기능**들을 더 많이 관리
- GKE가 리소스와 하드웨어 프로비저닝, 구성, 관리
- 간소화된 환경을 위해 Autopilot 클러스터 사용 권장

**특징**
- Google이 노드와 인프라 관리를 더 많이 수행
- 자동 스케일링과 효율적 스케줄링이 강하게 통합
- 보안 기본값과 권장 구성이 기본 적용
- 운영자가 인프라 세부 설정을 직접 손대는 범위 줄어듦
- 대부분의 일반적인 프로덕션 워크로드를 빠르게 운영하기 좋음

---
#### Standard vs Autopilot

**운영 책임 분배**

- **Standard**
	- 클러스터 운영자 책임
	- 노드와 노드풀 설계에 깊이 관여
	- 클러스터 설정 변경 자유도가 큼

- **Autopilot**
	- GKE가 더 많은 인프라 운영 담당
	- 사용자는 워크로드 명세와 서비스 운영에 집중
	- 제어권은 줄지만 운영 단순성이 커짐

**보안 기본값**

- Autopilot은 Google이 보안 모범사례와 제약을 기본 적용

**유연성과 제약**

- **Standard** : 세말한 제어 가능 / But, 그만큼 사용자가 더 많은 설계와 운영 책임

- **Autopilot** : 제약 존재/ But, 운영 단순성과 표준화를 얻음

**비용**

- **Standard**
	- 노드풀과 노드 단위 자원 설계 중요
	- 용량을 미리 잡는 사고가 더 익숙
	- 사용자는 노드 활용률 최적화에 더 신경 써야함

- **Autopilot**
	- 워크로드 명세를 기준으로 리소스가 더 직접적으로 연결
	- 과도한 프로비저닝 줄임
	- 클러스터 인프라 관리 < 워크로드 요청량 설계가 더 중요


>[!info] 요약
>GKE 클러스터 운영 모드 → Autopilot / Standard 제공  
>Autopilot → Google이 노드, 스케일링, 보안 기본 구성, 인프라 운영을 더 많이 관리 / 세밀한 제어 필요 X → Autopilot 사용 권장  
>Standard → 사용자가 노드풀, 보안 정책, 스케일링, 클러스터 설정을 더 많이 직접 제어  
>운영 책임 분배와 인프라 구성 자동화 수준에서 큰 차이  
>Standard → ComputeClass 통해 일부 워크로드를 Autopilot 방식으로 실행 가능  
>Autopilot → 릴리스 채널 등록이 필수, 버전 운영과 유지보수 전략도 플랫폼 중심  
>**Autopilot → 운영 자동화와 표준화 / Standard → 유연성과 제어**
